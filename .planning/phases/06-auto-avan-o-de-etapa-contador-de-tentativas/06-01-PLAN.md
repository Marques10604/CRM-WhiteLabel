## Decisões do planner (discrição delegada por 06-CONTEXT.md / Open Questions do 06-RESEARCH.md)

1. **Nome/forma do campo:** `contactAttempts` → coluna `contact_attempts`, `integer NOT NULL DEFAULT 0` (não nullable). Motivo: `DEFAULT 0` é semanticamente honesto para todo lead pré-existente e elimina fallback `?? 0` em toda leitura de UI.
2. **`lastContactedAt` NÃO é incluída** (Open Question 1 do RESEARCH, Assumption A3). Nenhum requisito de v1.2 (WA-06/07/08) pede timestamp de último contato; adicionar agora seria escopo especulativo. Se a todo `2026-07-21-sequencia-follow-up-escalonada.md` for construída depois, é uma migração aditiva trivial.
3. **Sem `db.transaction()` explícito** (Open Question 2 do RESEARCH). Há exatamente um `UPDATE` na action, e um único `UPDATE` já é atômico no SQLite. Uma transação Drizzle aqui só adicionaria a restrição de callback síncrono do driver `better-sqlite3` sem ganho.
4. **Função dedicada, não extensão de `updateLeadStage`.** `updateLeadStage` recebe etapa-alvo explícita do chamador e tem semântica de `motivoPerda`; o auto-avanço é unidirecional e estritamente condicional, e a guarda pertence ao servidor (RESEARCH Pattern 2).
5. **Retorno `{ advanced: boolean }`, não `ActionState`.** O chamador é fire-and-forget (a aba do WhatsApp já abriu) e só precisa saber se deve exibir o toast. Erros nunca são exibidos ao admin nesse fluxo, então o formato `{ errors }` não tem consumidor aqui. Falha de validação/lead inexistente retorna `{ advanced: false }` silenciosamente.

## DESVIO da convenção `generate` + `migrate` — obrigatório, verificado neste planejamento

`06-RESEARCH.md` (linha ~350) e `06-PATTERNS.md` afirmam a convenção "sempre `npx drizzle-kit generate` + `migrate`, nunca `push`". **Essa convenção não pode ser seguida nesta fase** — o snapshot de migração já divergiu do banco real. Evidência coletada diretamente no planejamento (`src/db/migrations/meta/0002_snapshot.json` vs. `data/crm.db`):

| Objeto | Existe no banco real | Existe no snapshot 0002 |
|--------|----------------------|--------------------------|
| tabela `templates` + índice `templates_tipo_idx` | sim | **não** |
| coluna `leads.import_batch_id` + índice `leads_import_batch_id_idx` | sim | **não** |
| coluna `subnichos.deleted_at` + índice `subnichos_deleted_at_idx` | sim | **não** |

Consequência concreta: `npx drizzle-kit generate` produziria uma migração com `CREATE TABLE templates`, `ALTER TABLE leads ADD import_batch_id` e `ALTER TABLE subnichos ADD deleted_at` **além** da coluna desta fase, e `npx drizzle-kit migrate` falharia em runtime (`duplicate column name: import_batch_id` — o SQLite não tem `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`). Não é hipótese: `__drizzle_migrations` no banco tem exatamente 3 linhas (0000/0001/0002) e as 3 divergências acima foram aplicadas via `push` nas Fases 04-02 e no quick task 260725-lai.

**Decisão:** aplicar a coluna com `npx drizzle-kit push` (Task 3), que diffa contra o banco real e emite só o `ALTER TABLE leads ADD contact_attempts`. **Não rodar `generate` nesta fase.** Reconciliar o snapshot com o banco (dívida herdada de 04-02) é um trabalho separado, sem relação com WA-06/07/08 — registrar como débito no SUMMARY, não resolver aqui.

## Limitações conhecidas e aceitas (documentar no SUMMARY, não "corrigir")

- **Corrida com o drag-and-drop otimista do board (Pitfall 5 do RESEARCH):** `registerWhatsAppContact` não participa do `useOptimistic`/`startTransition` de `pipeline-board.tsx`. Se o admin arrastar um card e clicar em "Abrir WhatsApp" do mesmo lead na mesma janela de tempo, dois SELECT-then-UPDATE independentes competem pela linha sem lock. Aceito deliberadamente (ferramenta solo, uma aba): o pior caso é "um lead que deveria mostrar Contatado ainda mostra Novo", recuperável reenviando ou pelo dropdown manual de etapa — a mutação nunca sobrescreve `negociacao`/`fechado`/`perdido` definidos manualmente, porque o gate exige `stage === "novo"`.
- **`/importar/[batchId]` não é revalidada** (rota dinâmica): `revalidatePath` cobre `/`, `/pipeline` e `/leads`. Nenhuma dessas telas de pós-importação exibe o contador (WA-08 pede visibilidade no card do pipeline), então o único efeito é a etapa exibida ali só atualizar no próximo carregamento.
- **`data/crm.db` é gitignored:** a Task 3 não produz diff versionável. A evidência de aplicação é a saída dos comandos de verificação, que deve ser colada no SUMMARY (mesmo precedente de `04-02-SUMMARY.md`).
