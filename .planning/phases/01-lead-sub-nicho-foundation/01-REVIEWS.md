# Cross-AI Plan Review — Phase 1: Lead & Sub-nicho Foundation

**Note:** `claude` was skipped as a reviewer (self — this review was run from inside Claude Code, per the workflow's self-exclusion rule for independence). No other CLIs (`gemini`, `coderabbit`, `opencode`, `qwen`, `cursor`, local model servers) were detected/requested on this system. Only `codex` was invoked, per the `--codex` flag.

## Codex Review

### Overall Summary

The four-plan sequence is strong: it builds the risky infrastructure first, proves one full vertical slice before leads, then layers lead CRUD, table interactivity, and soft-delete in a sensible dependency order. The plans are mostly well-scoped for Phase 1 and directly map to LEAD-01 through LEAD-04 and REMIND-02. Main risks are around version-sensitive tooling, incomplete treatment of date/phone/value normalization, client/server action error contracts, and a few UI edge cases that could create subtle regressions if not specified before implementation.

---

#### PLAN 01-01 — Walking Skeleton

**Strengths**
- Good first slice: sub-nicho CRUD proves UI → Server Action → Zod → Drizzle → SQLite → revalidation.
- Correctly prioritizes DB-level case-insensitive uniqueness instead of relying only on app checks.
- Explicit live DB migration verification is valuable; it avoids "build passes but schema is wrong."
- Creating both `leads` and `subnichos` upfront is reasonable because the FK relationship shapes the data model.
- Strong constraint discipline: no `app/api/*`, no auth, no premature CRM features.

**Concerns**
- **HIGH:** The "human checkpoint" for `sonner` and `date-fns` may block basic scaffolding unless the acceptance criteria are explicit. Define what counts as approved.
- **MEDIUM:** "Near-duplicate" prevention is claimed, but the plan only guarantees normalized duplicate blocking. It will not catch `nutri` vs `nutricionista`, and that is explicitly out of scope. The wording should be tightened.
- **MEDIUM:** SQLite expression unique index syntax and Drizzle migration generation can be finicky. The plan should specify whether the index is generated by Drizzle schema or custom SQL migration.
- **LOW:** Sub-nicho rename can break user expectations if whitespace/case-only changes are silently normalized or rejected without clear messaging.

**Suggestions**
- Define normalization exactly: likely `trim`, collapse repeated internal whitespace, and lowercase for uniqueness comparison.
- Add a seed or manual verification path for one sub-nicho surviving server restart.
- Add a small action-level test for duplicate create and duplicate rename, not just UI verification.
- Document the package manager and lockfile expectations from the scaffold step.

**Risk Assessment:** MEDIUM. The architecture is sound, but greenfield scaffolding with very current versions, shadcn changes, Drizzle migrations, and better-sqlite3 on Windows makes the first wave the riskiest operationally.

#### PLAN 01-02 — Lead Create/Edit Vertical Slice

**Strengths**
- Correctly delivers the core business object early.
- The 9-field modal matches the product decisions and avoids feature sprawl.
- Reusing one create/edit dialog is appropriate for this scope.
- Good call using `useActionState` and validating through Zod on Server Actions.
- Explicit hard-delete prohibition is a useful safety rail before soft-delete exists.

**Concerns**
- **HIGH:** Value handling needs sharper specification. `valorEstimado` as integer cents is right, but the plan should define pt-BR input parsing, empty value behavior, rounding, and display formatting.
- **HIGH:** Phone handling is underspecified. Since WhatsApp is a later phase, bad phone normalization now can create cleanup work later.
- **MEDIUM:** `followUpDate` local-midnight normalization is mentioned, but the storage type is "UTC timestamp." The conversion contract should be exact: what is sent from the client, what is persisted, and how it is rendered back.
- **MEDIUM:** Lead update should validate that `subnichoId` exists and is active/valid, not only that the field is shaped correctly.
- **MEDIUM:** The behavior test examples are too thin for this phase. Empty name and valid payload do not cover the risky fields.
- **LOW:** "Base non-interactive list" plus row-click edit is already interactive; make sure keyboard accessibility and action affordances are not postponed indefinitely.

**Suggestions**
- Add tests for invalid `subnichoId`, invalid/empty phone, malformed date, invalid stage, and value parsing.
- Define allowed enum values for `canal` and `stage` in one shared source used by schema, UI, and badge.
- Specify form behavior for optional fields: `origem`, `valorEstimado`, `notas`, and `followUpDate`.
- Add an "at least one sub-nicho required before creating a lead" empty-state path or disabled save state.

**Risk Assessment:** MEDIUM. The vertical slice is well chosen, but this is where most domain data quality problems enter the system. Tightening normalization and error contracts would lower the risk.

#### PLAN 01-03 — Filter/Sort/Paginate

**Strengths**
- Correctly keeps filtering client-side for the expected data size.
- Date-range filtering explicitly addresses the off-by-one pitfall.
- Default sort by follow-up date aligns with the product promise: never miss follow-ups.
- Always-visible toolbar matches the user decision and keeps the workflow direct.
- TanStack Table is the right tool for this phase.

**Concerns**
- **MEDIUM:** Null/empty `followUpDate` sorting and filtering behavior is not specified. These leads need deterministic placement.
- **MEDIUM:** Pagination plus filters can create confusing empty pages if the current page index is not reset when filters change.
- **MEDIUM:** Date filters need a clear inclusive range contract.
- **LOW:** "Limpar filtros" should also reset date picker UI state, table column filters, and possibly sorting depending on intended behavior.
- **LOW:** Client-side filtering is acceptable now, but the plan should state a rough migration threshold more concretely.

**Suggestions**
- Define null follow-up behavior: for example, show after dated leads in ascending sort and exclude from date-range filters unless no date filter is active.
- Reset pagination to page 0 whenever any filter changes.
- Add visible active-filter state or a simple result count: "X leads encontrados".
- Add test data with mixed stages, sub-nichos, null dates, past dates, and future dates.

**Risk Assessment:** LOW to MEDIUM. This plan is straightforward, but table state edge cases can make the UI feel broken if not specified.

#### PLAN 01-04 — Soft-delete + Lixeira

**Strengths**
- Directly satisfies the "never permanently lost" promise.
- Confirmation dialog with the lead name is the right UX safeguard.
- `stopPropagation` on row actions is explicitly called out, which avoids a common table bug.
- Revalidating both `/` and `/lixeira` is correct.
- Instant restore matches the product decision and keeps the trash workflow lightweight.

**Concerns**
- **HIGH:** "Recoverable, never permanently lost" is not fully protected by grepping only `src/actions/` for `db.delete(`. Hard deletes could appear elsewhere, in scripts, migrations, or future utilities.
- **MEDIUM:** Soft-deleted leads should probably be excluded from edit/update paths unless intentionally restored first.
- **MEDIUM:** The plan does not specify whether deleting an already-deleted lead or restoring an active lead is idempotent.
- **MEDIUM:** Trash table reuse may accidentally preserve active-list row-click edit behavior unless explicitly removed.
- **LOW:** Lixeira should show `deletedAt` so the admin has context for what was removed and when.

**Suggestions**
- Add action-level tests for soft delete, restore, double delete, double restore, and active/trash query separation.
- Add a code convention: application actions must not call `db.delete()` for leads; if future cleanup scripts exist, they must be isolated and named clearly.
- Prevent editing deleted leads from normal edit routes/actions, or have update fail with a clear error.
- Include `deletedAt` in Lixeira sorting, probably newest deleted first.

**Risk Assessment:** LOW to MEDIUM. The feature is simple and well scoped. The main risk is overconfidence in the grep-based hard-delete guard and missing idempotency behavior.

---

#### Cross-Plan Risks

- **Version/tooling risk:** Next 16, React 19, shadcn Base UI, Drizzle, and better-sqlite3 are all version-sensitive. The plans correctly notice this, but implementation should verify early and record deviations.
- **Data normalization risk:** Sub-nicho names, phone numbers, currency, and dates need precise contracts before the database accumulates messy data.
- **Server Action contract risk:** Plans should define a consistent return shape for field errors, form errors, success payloads, and toast messages.
- **Testing gap:** The plans mention useful tests, but coverage is uneven. Most risk sits in actions and normalization, not visual rendering.
- **Accessibility risk:** Modal, combobox, date picker, icon buttons, and row-click editing all need keyboard/focus behavior checked, especially because shadcn primitive behavior may differ by version.

#### Final Assessment (Codex)

Overall risk: **MEDIUM**.

The phase is well decomposed and should achieve the five Phase 1 success criteria if implemented faithfully. The biggest improvements would be to make normalization rules explicit, strengthen action-level tests, define edge-case behavior for dates/nulls/idempotency, and avoid overstating "near duplicate" prevention when the actual Phase 1 mechanism is normalized exact duplicate blocking.
