## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser (lead-form-dialog) -> Server Action (createLead/updateLead) | Input dos 9 campos cruza para o servidor; revalidado com leadSchema no server |
| Server Action -> SQLite (Drizzle) | Escrita de lead via query parametrizada |
| lead-form-dialog -> subnichoId (FK) | Referência a sub-nicho deve existir na lista administrável |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-05 | Tampering | createLead/updateLead (mass-assignment) | mitigate | `leadSchema.safeParse(Object.fromEntries(formData))`; `parsed.data` contém apenas os 9 campos declarados — campos extras do FormData (inclui `$ACTION_*`, e um `id` forjado no create) são descartados; update usa `where(eq(leads.id, id))` com id validado |
| T-01-06 | Tampering | Validação apenas no client | mitigate | O react-hook-form/zodResolver é UX; a Server Action SEMPRE revalida com o mesmo `leadSchema` — client pode ser contornado via DevTools/requisição direta |
| T-01-07 | Tampering | subnichoId inválido / FK | mitigate | `subnichoId` validado como inteiro positivo por Zod; FK `onDelete: "restrict"` no schema garante integridade referencial no banco |
| T-01-08 | Information Disclosure | Erros de validação ao client | mitigate | Retornar só `error.flatten().fieldErrors` (mensagens de campo), nunca stack trace ou dados de outros leads (dado de saúde sensível — RESEARCH Security Domain) |
| T-01-SC | Tampering | Dependências npm | accept | Sem novas instalações neste plano (todas em 01-01, já auditadas); nada a mitigar aqui |
</threat_model>
