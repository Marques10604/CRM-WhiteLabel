| Browser (lead-form-dialog) -> Server Action (createLead/updateLead) | Input dos 9 campos cruza para o servidor; revalidado com leadSchema no server, valor/telefone normalizados no server |
| Server Action -> SQLite (Drizzle) | Escrita de lead via query parametrizada |
| lead-form-dialog -> subnichoId (FK) | Referência a sub-nicho deve existir na lista administrável (checada no banco por SELECT E por captura de violação de FK, não só na forma) |

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-01-05 | Tampering | createLead/updateLead (mass-assignment) | mitigate | `leadSchema.safeParse(Object.fromEntries(formData))`; `parsed.data` contém apenas os 9 campos declarados — campos extras do FormData (inclui `$ACTION_*`, e um `id` forjado no create) são descartados; update usa `where(and(eq(leads.id, id), isNull(leads.deletedAt)))` com id validado e guard de soft-delete |
| T-01-06 | Tampering | Validação apenas no client | mitigate | O react-hook-form/zodResolver é UX; a Server Action SEMPRE revalida com o mesmo `leadSchema` (incl. normalização de valor/telefone e pré-validação estrita de moeda) — client pode ser contornado via DevTools/requisição direta |
| T-01-07 | Tampering | subnichoId inválido / FK | mitigate | `subnichoId` validado como inteiro positivo por Zod, verificado por `SELECT` de existência real no banco antes de gravar, E protegido por backstop: `try/catch` ao redor do insert/update captura `SQLITE_CONSTRAINT_FOREIGNKEY` (do `onDelete: "restrict"`) e o mapeia para o mesmo erro de campo — fecha a janela de corrida check-then-write (sub-nicho apagado entre a checagem e a escrita) |
