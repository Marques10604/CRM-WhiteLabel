    **Assinatura / contrato (nome livre, sugestão `resolvePeriodoRelatorios`):**
    - Entrada: `params: { period?: string; from?: string; to?: string }` e `now: Date = new Date()`.
    - Saída: `{ preset: "30d" | "90d" | "tudo" | "custom"; range: PeriodRange; customInvalido: boolean; from?: string; to?: string }`.

    **Regras (nesta ordem):**
    1. `params.period === undefined` → `{ preset: "30d", range: resolvePeriodRange("30d", now), customInvalido: false }`.
    2. `params.period` é `"30d"` ou `"90d"` ou `"tudo"` → `{ preset: params.period, range: resolvePeriodRange(params.period, now), customInvalido: false }`.
    3. `params.period === "custom"`:
       a. Validar `from` e `to`: ambos presentes, ambos batendo `^\d{4}-\d{2}-\d{2}$`, ambos parseáveis (`parseISO` + `isValid` de `date-fns`). Se qualquer um falhar → **fallback**: `{ preset: "30d", range: resolvePeriodRange("30d", now), customInvalido: true }`.
       b. Clamp de data futura (D-06): seja `fromDate = startOfDay(parseISO(from))`, `toDate = endOfDay(parseISO(to))`. Se `fromDate` > `startOfDay(now)` → `fromDate = startOfDay(now)`. Se `toDate` > `endOfDay(now)` → `toDate = endOfDay(now)`.
       c. Se `fromDate.getTime() > toDate.getTime()` (inclusive após o clamp, cobre "to antes de from") → **fallback**: `{ preset: "30d", range: resolvePeriodRange("30d", now), customInvalido: true }`.
       d. Caso ok → `{ preset: "custom", range: { start: fromDate, end: toDate }, customInvalido: false, from, to }` (as strings `from`/`to` originais, não clampadas na string — o 14-02 pré-preenche o picker com elas; se a data foi clampada, o próximo submit do picker corrige).
    4. Qualquer outro valor de `params.period` (adulterado) → `{ preset: "tudo", range: resolvePeriodRange("tudo", now), customInvalido: false }` (fallback silencioso, idêntico ao que a página já faz hoje — NÃO é `customInvalido`, não mostra faixa).

    **Nunca lança.** Envolver o parse em `try/catch` OU garantir por guarda de regex + `isValid` que nenhum caminho joga. O doc-comment deve dizer, no espírito do de `resolvePeriodRange`: valor vem de `searchParams` (não-confiável), vira `Date` aqui antes de virar parâmetro do Drizzle (mitigação de SQLi/DoS via `from`/`to`, T-11-19/T-11-20 aplicados aos parâmetros novos), `customInvalido` distingue "usuário pediu custom e errou as datas" (mostra faixa) de "valor adulterado" (fallback mudo).

    Importar de `date-fns` o que faltar: `endOfDay`, `parseISO`, `isValid`, `isAfter` (a lista de import atual é `addDays, isBefore, isToday, startOfDay, subDays`).

## Trust Boundaries

| Boundary | Description | Data Crossing |
|----------|-------------|---------------|
| `searchParams` (`period`/`from`/`to`) → `/relatorios` | Valor 100% controlado pelo cliente / URL — pode ser `undefined`, string adulterada, payload de SQLi, data absurda | string → `Date` |
| `Date` resolvido → parâmetro do Drizzle (`gte`/`lte` nas 3 agregações) | O range vira `?` parametrizado, nunca interpolado | timestamp |

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
