## Trust Boundaries

| Boundary | Description | Data Crossing |
|----------|-------------|---------------|
| `PeriodoSelector` (client) → querystring | O componente monta `?period=custom&from=&to=` a partir de `Date`s escolhidos no `<Calendar>` | `Date` → string `yyyy-MM-dd` |
| querystring → `/relatorios` (servidor) | A validação REAL do intervalo é do 14-01 no servidor — o cliente é só conveniência | string |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-14-06 | Tampering | usuário edita `from`/`to` na URL pra formato inválido, contornando os date pickers | mitigate | O cliente NÃO é a barreira de validação — `resolvePeriodoRelatorios` (14-01) valida no servidor e cai em `30d` + faixa de aviso. O `PeriodoSelector` só monta URLs bem-formadas via `format(d, "yyyy-MM-dd")`; qualquer URL adulterada é problema do servidor, já coberto. |
| T-14-07 | Denial of Service | navegação em loop (o `router.push` re-renderiza, que re-dispara `navegarCustom`) | mitigate | `navegarCustom` só é chamado dentro de `handleInicioChange`/`handleFimChange` (event handlers do `onSelect` do `Calendar`), NUNCA num `useEffect` nem no corpo do render. Re-render por mudança de `searchParams` não re-dispara navegação. Mesmo padrão seguro de `handleChange` no componente atual. |
| T-14-08 | Tampering | modo custom mostra dados de um preset (dessincronização `customMode` vs `value` da URL) | mitigate | O valor exibido pelo `<Select>` é `customMode ? "custom" : value`; `customMode` é inicializado de `value === "custom"`. Ao escolher preset, `setCustomMode(false)` + `router.push` acontecem juntos. Acceptance criteria cobre "com `?period=custom` na URL o Select mostra 'Intervalo personalizado'". |
| T-14-SC | Tampering | supply chain | accept | Zero dependência nova — `Popover`/`Calendar`/`Button` são primitivos já no repo; `date-fns`/`lucide-react` já usados. |

</threat_model>
